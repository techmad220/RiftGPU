# RiftGPU v0.2 Runtime Foundations

RiftGPU v0.2 grows above the certified v0.1 transport core. The transport core remains intentionally small: backend discovery, capability routing, performance records, and dependency-injection seams stay in `vrb-core`; inference/runtime policy and operator semantics remain independent higher-level crates.

## Added runtime layers

### `vrb-residency`

Provides durable GPU-resource residency through an explicit owner/provider lifetime. It adds generation-aware reuse, capacity accounting, active lease safety, invalidation, and LRU eviction.

This does **not** change the shared-operator ABI ownership rule. Shared-operator native handles remain borrowed for callback duration only and may not be retained or closed by plugins. A durable residency provider owns the underlying Vulkan/HIP objects and returns an owned allocation lease.

### `vrb-attention-protocol`

Defines a strict versioned 64-byte control protocol for shared-resource scaled dot-product attention. It carries metadata only; Q/K/V/output tensor payloads remain in shared GPU allocations.

The protocol defines FP32, FP16, and BF16 tensor-size semantics, Q/K/V/O resource order, grouped-query/multi-query head grouping, causal mode, scale, target device, exact resource counts, checked size arithmetic, and fail-closed reserved fields.

Protocol support does not imply that a particular GPU attention kernel has been certified.

### `vrb-attention-reference`

Provides the independent bounded FP32 CPU correctness oracle for scaled dot-product attention. It implements numerically stable softmax, causal decode offsets, and grouped-query attention mapping.

Future HIP or Vulkan attention implementations must match this semantic oracle before hardware capability promotion.

### `vrb-kv-cache`

Provides a capacity-bounded KV-cache metadata service keyed by sequence and layer. KV blocks reference durable residency keys rather than raw OS/GPU handles. Appends are token-contiguous and eviction removes complete least-recently-used entries rather than partially corrupting an active sequence.

### `vrb-execution-plan`

Adds whole-workload cost-aware routing above the existing single-operation router. The planner uses dynamic programming across an ordered operation sequence and combines measured operator latency with directional backend-transition costs.

This prevents a locally faster kernel from winning when a Vulkan↔HIP transition would make the complete workload slower.

### `vrb-autotune`

Adds schema-versioned benchmark persistence keyed by GPU architecture, driver version, runtime version, plugin version, operation, datatype, workload shape, and alignment. Exact environment/shape matches can be projected into the existing `vrb-core::PerformanceTable` without widening the core contract.

Changing the environment fingerprint naturally invalidates stale tuning data instead of treating old measurements as universal hardware facts.

## Hardware capability policy

These foundations intentionally do not advertise new evidence-bearing hardware capabilities.

In particular, this change does not claim certified HIP attention, FP16/BF16 execution, quantized kernels, graph execution, or a persistent native HIP import implementation. Those capabilities require concrete backend/operator implementations and exact-head physical AMD certification before promotion.

The existing `PROVEN_ZERO_COPY` rule remains unchanged: software tests can validate contracts and loaders, but only the physical hardware gate can certify an implementation as evidence-backed zero-copy.

## Next hardware work

With these foundations in place, the next independently certifiable layers are:

1. a concrete Vulkan/HIP durable-residency provider;
2. FP16/BF16 and quantized shared GEMM operators;
3. a HIP/Vulkan shared attention implementation matching the CPU oracle;
4. execution-graph support behind capability detection;
5. persistent KV-cache allocations wired through the residency provider;
6. measured transition-cost collection feeding the planner and autotune database;
7. inference-engine adapters such as llama.cpp/Ridge, kept outside `vrb-core`.

Each hardware feature must be developed and certified on its own exact head SHA. Certified release tags remain immutable.
